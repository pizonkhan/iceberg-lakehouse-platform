Evidence for the Dagster orchestration work package, captured against the real
local stack (docker compose: MinIO, Nessie, Postgres, Trino 483) running via
`make up`, not simulated or mocked.

Versions: dagster 1.13.16, dagster-dbt 0.29.16, dagster-webserver 1.13.16, all
released together (2026-07-30) and mutually pinned (dagster-dbt 0.29.16 declares
dagster==1.13.16 exactly; dbt-core<1.12,>=1.7 covers this project's dbt-core
1.10.22). See .notes/decisions.md for the version research.

01-asset-graph-nodes.json
  Full assetNodes GraphQL query result against a running `dagster dev` webserver
  (http://127.0.0.1:3000/graphql), server_info confirmed dagster_webserver_version
  1.13.16. 46 assets total: 9 bronze (the ingestion asset, one output per source
  table), 9 staging, 13 silver, 9 dimensions, 6 facts, exactly matching the 37
  models in transform/lakehouse's own dbt manifest (elementary package models
  excluded by the `resource_type:model,package:lakehouse` selection) plus the 9
  bronze source tables. dependencyKeys on each node show the full chain: bronze
  feeds staging feeds silver feeds dimensions/facts, generated entirely from
  dagster-dbt's read of the dbt manifest plus this project's own bronze asset, not
  a hand-built lineage map.

02-materialize-dim-payment-method-cli.log
02-materialize-dim-payment-method-trino-state.json
  `dagster asset materialize -m orchestration.definitions --select
  dimensions/dim_payment_method`, a small (33-row) Type 1 dimension, run twice
  against the live Trino/Nessie stack. Dagster's own log shows the exact dbt
  command it issued (`dbt build --target trino --select
  lakehouse.marts.dimensions.dim_payment_method`), all 10 dbt data tests passing
  as Dagster asset checks in the same run. Confirmed independently via a direct
  Trino query (not through Dagster) before and after: row count unchanged (33,
  correct for an idempotent full-refresh rebuild of unchanged upstream data),
  loaded_at advanced to the exact time of the Dagster-driven build, proving
  Dagster genuinely re-executed the model against the real warehouse rather than
  only reflecting prior state.

04-column-lineage-dim-subscriber.json
  Column-level lineage for the same dim_subscriber materialization, pulled via
  the assetNodeOrError GraphQL query's assetMaterializations.metadataEntries,
  specifically the dagster/column_lineage entry (TableColumnLineageMetadataEntry).
  This is generated by dagster-dbt's fetch_column_metadata(with_column_lineage=
  True), which queries the warehouse for the built model's and its upstream
  refs' column schemas and derives column-to-column dependencies from the
  compiled SQL via sqlglot, not a hand-maintained mapping. Confirms genuinely
  nontrivial, non-1:1 lineage: for example churn_date_key depends on
  silver_subscriber_events.changed_at and .status (the window-function churn
  detection logic), effective_to and scd_version depend on .changed_at and
  .subscriber_id (the version-boundary window functions), previous_plan_tier
  depends on .changed_at, .plan_tier and .subscriber_id (the lag() call), and
  row_hash depends on .plan_tier and .status (the version-change hash). A
  simple 1:1 passthrough model would show one dependency per column; this
  fan-in pattern is what a real SCD transformation's lineage should look like,
  and it was derived automatically, not asserted.

Not captured as a separate file: the bronze ingestion asset itself was not
re-materialized for this work package's verification. It already holds the
project's real ingested data (bronze_playback_sessions alone is ~120M rows);
re-running it would append a second, duplicate load batch on top of that data,
which the "do not run destructive or duplicative operations against bronze"
scope for this work package rules out. The bronze asset's presence and its
dependency wiring into every staging asset is what 01-asset-graph-nodes.json
demonstrates instead: the graph is complete and contiguous even though this
particular node was not re-executed today.
