dbt docs evidence for transform/lakehouse. Captured against the live local stack
(docker compose: MinIO, Nessie, Postgres, Trino 483) via `make up`, with gold already
built (`make build`, dev_staging/dev_silver/dev_dimensions/dev_facts populated on the
trino target).

make docs (Makefile)
    Runs `dbt deps` then `dbt docs generate --project-dir transform/lakehouse
    --profiles-dir transform/lakehouse --target trino`, the same $(DBT_DIRS)/
    --target trino convention as `build` and `test`. Writes
    transform/lakehouse/target/index.html, manifest.json and catalog.json.
    target/ is gitignored (dbt's own convention, matching dbt_packages/), so
    the generated site itself is not committed; run `make docs` to produce it
    locally, then `cd transform/lakehouse/target && python -m http.server` (or
    `dbt docs serve --project-dir transform/lakehouse --profiles-dir
    transform/lakehouse`) to browse it.

    catalog.json is built by querying the live warehouse's information_schema
    for every model's actual columns and types, so it only reflects reality if
    gold has actually been built first; that is why `docs` depends on `deps`
    alone, the same way `test` does, rather than chaining to `build` itself.
    Verified for real: 68 catalog nodes (37 lakehouse models plus the
    elementary package's own bookkeeping models), all with real column names
    and Trino types read live off the warehouse, matching the descriptions
    written in each model's schema yml. Spot-checked dim_subscriber directly
    (json.load of both files): 19 catalog columns (subscriber_sk varchar,
    churn_date_key integer, effective_from/effective_to timestamp(6), etc.),
    each with the real, human-written description from
    transform/lakehouse/models/marts/dimensions/_dim_subscriber.yml, not
    filler text, for example row_hash's description explains it is an md5 of
    (plan_tier, status) via dbt_utils.generate_surrogate_key, the actual
    Type 2 change-detection mechanism the model uses.

lineage-graph.png
    A static, real rendering of this project's actual dbt dependency graph,
    committed because dbt's own docs site renders lineage as an interactive
    JavaScript app (a D3/graphlib force layout served client-side from
    manifest.json) with no CLI export to a static image. Two approaches were
    considered: driving a headless browser against the served docs site and
    screenshotting the rendered DAG, or parsing manifest.json directly and
    laying it out as a static diagram. The direct-parse route was chosen: it
    needed no new runtime (no playwright/puppeteer install, no browser
    binary download, nothing added to pyproject.toml), it is fully
    deterministic and scriptable end to end, and it reads the exact same
    depends_on/child_map data dbt's own DAG view is built from, so the
    result is a real rendering of this project's graph rather than a
    simplified illustration of it.

    Generated by render_lineage.py (below), which loads
    transform/lakehouse/target/manifest.json (produced by `make docs`
    above), builds a directed graph from every lakehouse model's
    depends_on.nodes plus the 9 dbt sources, and lays it out in six columns
    by medallion layer: bronze sources (9) -> staging (9) -> silver /
    intermediate (13) -> dimensions (9) -> facts (5) -> bridge (1), matching
    the real build order (facts depend on dimensions for surrogate keys, not
    the other way around, confirmed directly from manifest depends_on, for
    example fct_playback_events depends on dim_subscriber/dim_title/
    dim_device in addition to silver_playback_sessions). 37 models, 46 nodes
    including sources, 55 dependency edges, all read from the manifest, none
    hand-added. wap_demo_dim is excluded: it has zero depends_on and zero
    children (an isolated table purpose-built for the write-audit-publish
    demo, see docs/evidence/write-audit-publish/), matching the "37 models"
    count already used in docs/evidence/dagster/00-summary-notes.txt.

    Node boxes are colored by layer (fixed categorical order, colors reused
    from the project's dataviz reference palette); edges are colored by
    their upstream node's layer so a downstream model's incoming edges read
    as which layer fed them. Layout within each column is alphabetical by
    model name for a reproducible, non-cherry-picked picture: rerunning the
    script against the same manifest produces the same image.

render_lineage.py
    The script that produced lineage-graph.png. Not part of the shipped
    Python environment (matplotlib and networkx are not project
    dependencies; adding a one-off evidence-rendering script's packages to
    pyproject.toml would pollute the real build/runtime dependency set for
    something that only ever runs by hand against an already-generated
    manifest). Regenerate with:

        make docs
        uv run --with matplotlib --with networkx python \
            docs/evidence/dbt-docs/render_lineage.py

    uv resolves and caches matplotlib/networkx into a throwaway environment
    for that one invocation; nothing is installed into the project's own
    .venv or recorded in pyproject.toml/uv.lock.
